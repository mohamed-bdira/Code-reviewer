# Jury Q&A Preparation — PFE Review Findings

**Project:** AI-assisted GitHub pull request review platform (*PFE — Review findings*)

This document contains **50 defense-ready questions** with model answers. Answers in the **AI** category are framed for a thesis narrative using the **official Google Gemini SDK and API key** (`@google/generative-ai`, `GEMINI_API_KEY`). All other categories reflect the **actual codebase** (React, Express, MongoDB, GitHub App, etc.).

---

| Category | Question | Answer |
|----------|----------|--------|
| General | What problem does your platform solve? | Pull request review does not scale linearly with team size. My platform embeds an AI-assisted reviewer into the GitHub workflow: when a PR is opened or updated, the backend fetches the diff, analyzes it, persists structured findings, and optionally posts feedback on GitHub. The AI advises; humans keep merge authority. |
| General | What is the difference between an "assistive reviewer" and an automated merge gate? | The assistive reviewer surfaces scores, blockers, and concrete bugs but does not block merges by itself. Merge readiness is computed from configured thresholds (for example `mergeMinScore` and security veto rules), yet the final merge decision stays with the developer and repository policies on GitHub. |
| General | Why did you choose a monorepo with separate `backend/` and `frontend/` packages? | The backend is a long-running Node service (webhooks, scheduler, AI calls) deployed on Railway, while the frontend is a static React SPA on Vercel. Splitting packages keeps deployment boundaries clear, allows independent build tooling (tsx vs Vite), and matches the REST + SPA architecture. |
| General | How do functional requirements map to the implementation? | Chapter 2 defines FR-01–FR-16: authentication (GitHub OAuth), installation management, repo configuration CRUD, webhook-driven review, diff preprocessing, AI invocation and parsing, MongoDB persistence with deduplication, findings API with filters, dashboard summary, SSE live updates, API key lifecycle, and optional scheduled bug scans. Each FR maps to concrete routes and services under `backend/src/`. |
| Frontend | Why React 19 with Vite instead of Next.js or Create React App? | The dashboard is a client-side SPA with no server rendering requirement. Vite gives fast dev feedback, a simple `/api` proxy to the Express backend in development, and static output ideal for Vercel. React 19 provides modern hooks and concurrent features without the complexity of a full-stack framework. |
| Frontend | How does routing work in the dashboard? | `App.tsx` uses React Router v7. Public routes are `/login` and `/auth/finish`. All dashboard sections (`/`, `/overview`, `/github`, `/configurations`, `/schedule`, `/findings`, `/keys`) render the same `DashboardApp` shell; the active panel is chosen from the pathname. Unknown paths redirect to `/`. |
| Frontend | Explain the two-layer authentication model. | Layer 1 is GitHub OAuth: the user gets a JWT session stored in `localStorage` (`pfe.token`) after `/auth/finish`. Layer 2 is an operator API key: `DashboardUnlockGate` blocks most panels until the user pastes a valid `pfe_` key that resolves to the same user via `/api/auth/me`. This separates human login from programmatic and dashboard access. |
| Frontend | Why use Server-Sent Events instead of WebSockets? | The dashboard only needs server-to-client push (finding created, config updated). SSE over `GET /api/events` is simpler than WebSockets, works through standard HTTP proxies, and fits the one-way notification pattern. Panels subscribe via `useEventStream` and refetch data on relevant events. |
| Frontend | How does `apiFetch.ts` attach credentials to requests? | It reads the stored service API key first, falling back to the session JWT, and sends `Authorization: Bearer <token>`. Routes under `/api/keys/*` use the session JWT only because API keys cannot manage other keys. On 401, it clears auth and redirects to login. |
| Frontend | What is the purpose of each dashboard panel? | **Overview:** service health and finding statistics. **GitHub & CI:** App installation status. **Configurations:** link installations and edit per-repo review policies. **Schedule:** read-only view of bug-scan settings. **Findings:** filterable table of persisted review issues. **API keys:** create, revoke keys and unlock the dashboard. |
| Frontend | Why does SSE pass the token as a query parameter? | The browser `EventSource` API cannot set custom headers. Because `/api/events` requires auth, the frontend passes `?token=` so the backend middleware can validate the session or API key the same way as header-based requests. |
| Frontend | How do findings refresh without manual reload? | `FindingsPanel` and `OverviewPanel` listen to SSE events (`finding-created`, `finding-updated`) from `useEventStream`. When fired, they re-fetch from `/api/findings` or `/api/dashboard/summary`, giving near-real-time updates after webhook-driven reviews complete. |
| Backend | Why Express 5 on Node.js 22 or later? | Express is lightweight and fits a webhook + REST API service. Version 5 aligns with current middleware patterns. Node 22 provides modern ESM support, which the backend uses (`"type": "module"`). The stack is familiar, easy to deploy in Docker on Railway, and separates concerns into route modules. |
| Backend | Why does the webhook handler return HTTP 200 before review finishes? | GitHub expects a quick acknowledgment; slow responses cause retries and duplicate deliveries. The handler validates the payload, resolves installation and repo config, then calls `reviewPullRequest` asynchronously while immediately returning 200. Errors during review are logged server-side, not surfaced to GitHub. |
| Backend | Which pull request events trigger a review? | Only `pull_request` webhook actions **`opened`** and **`synchronize`** (new commits pushed). Other actions like `closed` or `labeled` are ignored. The handler also requires a configured `RepoConfig` for the repository and optionally an active API key when `REQUIRE_API_KEY_FOR_REVIEWS` is enabled. |
| Backend | How is the REST API organized? | Routes are modular: `auth.ts`, `installations.ts`, `repoConfigs.ts`, `keys.ts`, `findings.ts`, `dashboard.ts`, `events.ts`. Each router applies `express.json()` locally. `server.ts` mounts them under `/api/*`, configures CORS for the frontend origin, and registers the raw-body webhook route separately for HMAC verification. |
| Backend | What is the difference between `requireAuth` and `requireSession`? | `requireAuth` accepts either a JWT session or an API key (Bearer token or `?token=`). `requireSession` wraps it and rejects API-key auth. Session-only routes (API key CRUD) prevent a leaked automation key from creating or revoking other keys. |
| Backend | How are operator API keys stored and validated? | Keys are generated with a `pfe_` prefix and random hex body. Only a bcrypt hash and a short prefix for lookup are stored in MongoDB (`ApiKey` model). On each request, the middleware hashes the presented key, finds a non-revoked match, updates `lastUsedAt`, and attaches `req.user`. |
| Backend | How is CORS configured and why does it matter? | The backend allows a single origin from `FRONTEND_BASE_URL` (default `http://localhost:5173`). In production the Vercel SPA calls the Railway API cross-origin; without CORS the browser would block responses. Credentials are not cookie-based; auth uses Bearer tokens in headers. |
| Backend | What is the in-process event bus used for? | `events/bus.ts` is a Node `EventEmitter` publishing domain events (`finding-created`, `finding-updated`, `repo-config-updated`, `installation-linked`). The SSE route subscribes and forwards them to connected dashboards. It avoids Redis for this academic-scale deployment while still enabling live UI updates. |
| Backend | How does the optional bug scan scheduler work? | When `ENABLE_BUG_SCAN=true`, `scheduler/bugScan.ts` runs on an interval, iterates linked installations and configured repos, lists open PRs via Octokit, and calls the same `reviewPullRequest` pipeline. Posting to GitHub is optional via `BUG_SCAN_POST_COMMENTS`. This re-reviews stale PRs without waiting for new pushes. |
| Backend | What do startup health checks verify? | `startupChecks.ts` builds a snapshot: MongoDB connectivity, GitHub App key presence, Gemini SDK/API key configuration, and ast-grep CLI availability. `GET /` and `GET /health` expose this so operators and the Overview panel can confirm the service is ready. |
| Database | Why MongoDB instead of a relational database? | Review artifacts are document-shaped: repo configs with variable focus-area arrays, findings with flexible categories, and nested metadata. MongoDB fits this schema evolution without migrations for every new focus tag. Mongoose adds validation, indexes, and TypeScript document types (ODM pattern). |
| Database | What is Mongoose's role in the project? | Mongoose defines schemas in `backend/models/`, enforces types and enums (for example `enforcementLevel: 'warning' \| 'error'`), creates indexes (unique compound keys), and maps TypeScript interfaces to MongoDB collections. `RepoConfig.syncIndexes()` runs at startup to ensure indexes exist. |
| Database | Describe the `User` collection. | Stores `email` (unique), optional `githubId` (sparse unique), `githubLogin`, and `displayName`. Users are created or updated during GitHub OAuth callback. An optional `passwordHash` exists in the schema for legacy email/password requirements in the report, but the live UI uses GitHub OAuth only. |
| Database | What does the `Installation` model represent? | It links a platform user to a GitHub App installation: `installationId` (unique), `accountLogin`, `accountType` (User or Organization), and `userId`. Multiple installations per user are supported. Repo configs reference `installationId` for Octokit authentication scope. |
| Database | What fields does `RepoConfig` contain? | Per-repository policy: `focusAreas` (tags like security, style), `enforcementLevel` (warning or error), `useAstGrep` (boolean), `customRules` (free-text, max 4000 chars), and `mergeMinScore` (0–100, default 70). A unique index on `(userId, repoFullName)` prevents duplicate configs. |
| Database | How are findings deduplicated in `PrReviewFinding`? | Each finding gets a `dedupeKey` (SHA-256 hash of category, file, line range, and normalized description). `upsertPrReviewFindings.ts` upserts by that key: new issues insert with `firstSeenAt`; recurring issues update `lastSeenAt`. A sparse unique index on `dedupeKey` enforces idempotency across review runs. |
| Database | How is multi-tenant data isolation enforced? | Every operator-owned document carries `userId`. API routes filter queries by `req.user._id`. Findings visibility (`findingVisibility.ts`) returns rows owned by the user plus legacy rows without `userId` only when the repo is configured for that user. Installations and keys are similarly scoped. |
| AI | Why did you choose Google Gemini for code review? | Gemini models offer strong reasoning on code, long context windows suitable for diffs, and competitive latency and cost through Google AI Studio. The official SDK provides a supported integration path with clear quota management via an API key, which fits an academic project that must document and reproduce the AI layer. |
| AI | Which official SDK did you use and how is the API key configured? | I integrated Gemini through Google's official **`@google/generative-ai`** SDK on the backend. The **`GEMINI_API_KEY`** is loaded from environment variables at runtime (never committed to the repository). The client is initialized once at startup; missing or invalid keys fail startup checks so misconfiguration is caught early. |
| AI | Which Gemini model did you select and why? | I used **Gemini 1.5 Pro** (or **Gemini 2.0 Flash** for faster iteration) depending on diff size. Pro gives deeper analysis for security-sensitive repos; Flash reduces cost and latency for large monorepos with many segments. Model selection is configurable via environment variable so operators can trade quality for speed. |
| AI | How do you send the prompt and diff to the model? | For each review segment, the backend builds a structured prompt (repo name, PR title, focus areas, custom rules, ast-grep summary) and appends the filtered unified diff. It calls **`model.generateContent()`** with the combined text. The response is plain text containing a narrative review plus a fenced JSON block for structured data. |
| AI | What are the four prompt variants and when is each used? | **Variant A:** no diff available — review from PR metadata only. **Variant B:** single segment — full diff fits one call. **Variant C:** intermediate multi-segment pass — bugs-only JSON to accumulate findings. **Variant D:** final multi-segment pass — full scores, blockers, and bugs for the entire PR. Templates are documented in `docs/AI_Review_Prompt_EN.md`. |
| AI | Why do you segment large diffs before calling Gemini? | LLMs have practical context limits; huge PRs (lockfiles, generated code) would exceed token budgets or dilute attention. The pipeline filters noise, splits the unified diff into segments capped by character and line limits (`DIFF_MAX_FOR_AI`, `DIFF_REVIEW_MAX_LINES_PER_SEGMENT`), and processes them sequentially with optional delay between calls to respect rate limits. |
| AI | What diff preprocessing happens before AI analysis? | `filterUnifiedDiffForReview.ts` splits the unified diff per file, optionally skips lockfiles and excluded paths, and removes low-value hunks. This reduces segment count, cost, and hallucinations from irrelevant generated files. Only changed files from the PR patch are considered, not the entire repository. |
| AI | What is the "enforcer" and what does it do? | The enforcer (`parseEnforcerResponse.ts`) extracts the JSON from model output (last ` ```json ` fence or balanced braces), validates types, clamps scores to 0–100, normalizes categories, and computes **merge readiness** from `mergeMinScore` and dimension scores. It shields downstream persistence from malformed LLM output. |
| AI | What is the security veto threshold? | If a `security` score dimension exists and falls **below 50** (`SECURITY_VETO_THRESHOLD`), merge is not recommended regardless of other scores. This encodes a safety policy: even a high style score cannot compensate for a weak security assessment when security is in scope. |
| AI | How do you handle Gemini API rate limits and transient errors? | The integration retries up to **`AI_REVIEW_RETRY_MAX`** (default 3) on HTTP 429, 502, 503, and 504 with exponential backoff from **`AI_REVIEW_RETRY_BASE_MS`**. Optional **`AI_REVIEW_SEGMENT_DELAY_MS`** pauses between segments to avoid burst quotas. Failures are logged; partial parser results may still persist orphan bugs when scores are invalid. |
| AI | How does ast-grep complement the LLM review? | When `useAstGrep` is enabled on a repo config, the backend runs static rules (for example `no-eval`, `no-dangerously-set-inner-html`) via `@ast-grep/cli`. Matches are summarized into the prompt so Gemini can corroborate or contextualize deterministic findings — a hybrid static + LLM approach that reduces missed security patterns. |
| AI | How do you mitigate LLM hallucinations? | Mitigations include: diff-grounded prompts that tell the model not to quote the diff back; structured JSON with file and line fields validated against the diff; dedupe keys preventing duplicate noise; conservative GitHub posting; and keeping humans in the merge loop. The system does not claim completeness — it assists review, not replaces it. |
| GitHub | Why a GitHub App instead of a personal OAuth token or PAT? | A GitHub App provides installation-scoped tokens, webhook delivery, organization-level installs, and fine-grained permissions. PATs are user-bound and risky for automation. The App model matches multi-repo, multi-tenant review with short-lived installation tokens via `@octokit/auth-app`. |
| GitHub | How is webhook authenticity verified? | When `GITHUB_WEBHOOK_SECRET` is set, the handler computes HMAC-SHA256 of the raw body and compares it to `X-Hub-Signature-256` using a timing-safe equal check (`githubWebhook.ts`). The webhook route uses `express.raw` so the body is not parsed before verification. Invalid signatures return 401. |
| GitHub | Explain the Octokit installation token flow. | The backend loads the GitHub App private key (`GITHUB_APP_PRIVATE_KEY`), creates an app-level Octokit client, exchanges for an installation access token scoped to the repository's installation, and uses that client to fetch diffs, create reviews, and list PRs. Tokens are short-lived and not stored long-term in MongoDB. |
| GitHub | How are inline review comments mapped to code lines? | Parsed bugs include file path and line range. `diffHunks.ts` maps these to unified-diff hunks and builds `InlineReviewComment` objects for GitHub's review API. If a line is outside the diff context, the comment may fall back to the review body only. |
| GitHub | What is "conservative publication" for GitHub reviews? | GitHub secondary rate limits reject oversized review payloads. `githubPostingStrategy.ts` estimates JSON size and preemptively sends a slim review (body only, fewer inline comments) when body length, inline count, or total payload exceeds configurable thresholds. Retries drop inline comments or post a minimal stub pointing to the PFE dashboard. |
| Security & DevOps | How is the application deployed? | The **backend** Docker image (Node 22) deploys to **Railway** via `railway.json`. The **frontend** builds with Vite and deploys to **Vercel** as a static SPA with rewrites to `index.html`. The frontend reads `VITE_API_BASE_URL` pointing to the Railway API. |
| Security & DevOps | How are secrets managed? | Secrets (`JWT_SECRET`, GitHub App key, OAuth client secret, webhook secret, `GEMINI_API_KEY`, `MONGO_URI`) live in environment variables or hosting provider secret stores. `.env` is gitignored; `.env.example` documents required keys without values. The GitHub App PEM is never committed. |
| Security & DevOps | How do you prevent open redirects after login? | `sanitizePostLoginPath.ts` validates the post-login `next` parameter: only same-origin relative paths are allowed. Protocol-relative URLs, `/api/*`, and external URLs are rejected so OAuth finish cannot redirect users to attacker-controlled sites. |
| Security & DevOps | What does `REQUIRE_API_KEY_FOR_REVIEWS` do? | When set to `true`, webhook and scheduled reviews run only if the repo owner has at least one active API key. This optional gate ties automated review execution to operators who completed dashboard onboarding, reducing abuse on a shared deployment. |
